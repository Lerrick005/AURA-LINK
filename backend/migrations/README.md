# Migration Policy

**Migrations are hand-written. `alembic revision --autogenerate` is exploratory only and its output must never be committed or applied blindly.**

## Why

Auralink deliberately mixes two schema-management strategies:

### ORM-managed tables (have SQLAlchemy classes)
For these, the model is the source of truth and a drift test enforces consistency
(`tests/db/test_orm_schema_drift.py`).

- `agents`, `agent_versions`, `tools`, `agent_tool_grants`, `agent_runs`
- `users`, `organizations`, `memberships`, `sessions`

### Raw-SQL-managed tables (no ORM classes by design)
These are created by hand-written migrations and accessed via `text()` SQL only.
They have no ORM class because:
- They need JSONB adaptation or column-level grants SQLAlchemy can't express cleanly
- They're append-only audit/execution logs where ORM lifecycle hooks are a liability
- Their access paths are hot and controlled (raw SQL = predictable queries)

- `execution_steps`, `tool_calls`, `escalations`
- `audit_log`
- `run_context`

## Rules

1. Never commit an autogenerated migration.
2. Run `alembic revision --autogenerate -m "exploratory"` only to *investigate*
   drift. Read the output, then **delete the generated file**.
3. Write migrations by hand with clear design notes in the docstring.
4. Every schema change ships with a migration (Rule 9 of the master prompt).
5. If a table moves from raw-SQL-managed to ORM-managed, that transition is
   its own ADR.
